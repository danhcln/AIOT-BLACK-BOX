# Project Rules Priority & KiCad Safety Protocols

In all interactions, decisions, and modifications, follow this strict priority order:

1. **Verified hardware / Manufacturer datasheets**
   - Espressif ESP32-S3 datasheet & technical reference manual
   - Module vendor hardware schematics and pinouts
   - Component IC datasheets (LDO, charging IC, IMU, GPS, SD card)

4. **User's explicit current instruction**

5. **Selected ECC workflow**

6. **General agent defaults**

## 2. Approved System Power Architecture

### A. Primary Power Source vs. External Input
- **PRIMARY POWER SOURCE**: **`18650 Li-ion Battery / VBAT`**.
- **EXTERNAL CHARGING/INPUT**: **`USB-C / VBUS`** is NOT the primary operating power source; it is strictly the external charging/input source.
- **Official Relationship**:
  `USB-C / VBUS` → `BATTERY CHARGING / POWER MANAGEMENT` → `18650 / VBAT` → `POWER CONVERSION / DISTRIBUTION` → `SYSTEM POWER RAILS (5V_SYS & 3V3_SYS)`

### B. Protected Power Domains
- **`VBUS`**: External USB-C charging/input source
- **`VBAT`**: 18650 battery / **PRIMARY POWER SOURCE**
- **`5V_SYS`**: Regulated 5V system power rail (supplies ESP32 DevKit power input, 5V buzzer circuit, and other verified 5V loads)
- **`3V3_SYS`**: Regulated 3.3V peripheral/logic system rail
- **`GND`**: Common system return
- **`ADC_VBAT_SENSE`**: Battery voltage measurement divider channel connected to **`GPIO1`**

> [!IMPORTANT]
> **Strict Power Domain Invariants**:
> - **`5V_SYS` is the official project net/domain name.** Do NOT silently rename `5V_SYS` to `+5V`.
> - **Do NOT merge `VBUS` and `5V_SYS`**; they represent different functional locations in the power architecture.
> - **`3V3_SYS` is an independent system rail.** It is NOT "3.3V generated by the ESP32 DevKit for all peripherals".
> - **The ESP32 DevKit must NOT be treated as the central power distributor** for external peripherals. ESP32 and peripheral modules are **LOADS** of the system power architecture.
> - Do not silently rename or merge these power domains.

### C. Peripheral Power & Signal Rules
- **Module Voltage Verification**: Before assigning a module to `3V3_SYS` (MPU6050, DS3231, OLED, MicroSD, NEO-M8N, other 3.3V logic), verify its actual breakout-board input-voltage requirements. Do not infer module supply voltage solely from the IC voltage.
- **4G Module Power**: Power requirements for MKE-M21 / SIM7680C must be verified against the physical board before final hardware design. Do not assume `5V_SYS` is valid merely because the presentation schematic uses that relationship.
- **ESP32 Signals are NOT Power Sources**: GPIO connections (I2C, SPI, UART, INT, PPS, CS, PWRKEY, STATUS, CANCEL, BUZZER_CTRL) are purely signal paths and must never be interpreted as supplying operating power.

### D. No Hardware Invention
- This is an **architectural specification**. Exact DC-DC / regulator components are **NOT yet frozen**.
- Do NOT invent specific regulator part numbers, boost converters, charger ICs, power-path ICs, or current ratings until verified against hardware requirements and power budget.

## 3. Non-Negotiable Circuit Safety Constraints

- **No Unsolicited Redesign**: Never alter power distribution, substitute major components, or rewrite net mappings without explicit user instruction.
- **Lock File Respect**: Always check for `.lck` files before modifying schematic files. Never remove, override, or edit a locked file.
- **Scope Containment**: Every edit must touch the absolute minimum number of elements necessary.
- **Physical Module Accuracy**: Never invent pin orders or omit real physical pins. Unused exposed pins must have visible pins with KiCad `no_connect` symbols attached.
- **Power Pin Elevation Rule**:
  - Positive power (`VBUS`, `VBAT`, `5V_SYS`, `3V3_SYS`): Must be on the UPPER portion of the symbol.
  - Ground (`GND`): Must be at the VERY BOTTOM of the symbol.
  - Pin orientation: Horizontal exit only (left or right).
- **No Unverified Completion Claims**: Never claim a task is DONE, PASSED, or READY without running ERC and inspecting exports.

## 4. ECC Workflow Invocation Policy

- **Normal schematic modifications**: `planner` → modification → `verification-loop`
- **Schematic defects / ERC errors / wrong nets**: `orch-fix-defect` → `verification-loop`
- **Major revisions (e.g. REV8)**: `planner` → modification → `verification-loop` → `code-reviewer`
- **Context auditing**: `context-budget` (manual audit only; auto-invocation disabled).
