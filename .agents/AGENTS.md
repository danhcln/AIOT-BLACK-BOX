## 2. Approved System Power Architecture

### A. Primary Power Source vs. External Input
- **PRIMARY POWER SOURCE**: **`18650 Li-ion Battery / VBAT`**.
- **EXTERNAL INPUT / CHARGING**: **`USB-C / VBUS`** is strictly the external charging and input source, NOT the primary operating power source.
- **Official Power Relationship**:
  ```text
  USB-C / VBUS (External 5V Input / Charging Source)
      ↓
  BATTERY CHARGING / POWER MANAGEMENT
      ↓
  18650 / VBAT (Primary Operating Power Source)
      ↓
  POWER CONVERSION / DISTRIBUTION
      ↓
  SYSTEM POWER RAILS (5V_SYS & 3V3_SYS)
  ```

### B. Separate System Power Rails & Protected Domains
The project strictly defines separate system power domains:
1. **`VBUS`**: External USB-C charging/input source.
2. **`VBAT`**: 18650 Li-ion battery rail / **PRIMARY POWER SOURCE**.
3. **`5V_SYS`**: Regulated 5V system power rail (supplies ESP32 DevKit power input, 5V buzzer circuit, and other verified 5V loads).
4. **`3V3_SYS`**: Regulated 3.3V peripheral/logic system rail (supplies low-voltage peripherals and logic).
5. **`GND`**: Common system return.
6. **`ADC_VBAT_SENSE`**: Battery voltage measurement divider channel tied to **`GPIO1`**.

> [!IMPORTANT]
> **Key Power Architecture Rules**:
> - **`5V_SYS` is the official project net/domain name.** Do NOT rename `5V_SYS` to `+5V`.
> - **Do NOT merge `VBUS` and `5V_SYS`**; they represent distinct functional stages in the power path.
> - **`3V3_SYS` is an independent system rail**, NOT defined as "3.3V generated by the ESP32 DevKit for all peripherals".
> - **The ESP32 DevKit must NOT be treated as the central power distributor** for external peripherals. Both the ESP32 and peripheral modules are **LOADS** of the system power architecture.
> - Do not silently merge, rename, or invent additional power domains.

### C. Peripheral Power & Signal Boundaries
- **Module Voltage Verification**: Before assigning a module to `3V3_SYS` (e.g. MPU6050, DS3231, OLED, MicroSD, NEO-M8N), verify its actual breakout-board input voltage requirements. Do not infer module power supply needs solely from IC voltage.
- **4G Module Power**: Power requirements for MKE-M21 / SIM7680C must be verified against the physical board before final hardware design. Do not assume `5V_SYS` is valid merely because the presentation schematic used that relationship.
- **ESP32 Signals are NOT Power**: GPIO connections (I2C, SPI, UART, INT, PPS, CS, PWRKEY, STATUS, CANCEL, BUZZER_CTRL) are purely signal paths and must never be interpreted as supplying operating power.

### D. No Hardware Invention
- This is an **architectural specification**. Exact DC-DC / regulator components are **NOT yet frozen**.
- Do NOT invent specific regulator part numbers, boost converters, charger ICs, power-path ICs, or current ratings until hardware requirements and power budgets are physically verified.

## 3. KiCad-Specific Safety Protocol

Before modifying any production schematic:

```text
READ PROJECT RULES
  → CHECK KICAD LOCK (*.lck)
  → CREATE TIMESTAMPED BACKUP
  → PLAN MINIMAL MODIFICATION
  → MODIFY MINIMUM NECESSARY AREA
  → RUN ERC (kicad-cli)
  → EXPORT PDF / SVG
  → VISUALLY VERIFY RENDER
  → REGRESSION CHECK PROTECTED CIRCUITS
  → REPORT
```

### Safety Invariants:
1. **Never delete or bypass an active KiCad lock (`*.lck`)**: If a lock exists, wait or notify the user; KiCad may be actively open.
2. **Never modify PCB files (`*.kicad_pcb`)**: Unless explicitly requested by the user.
3. **Never modify global KiCad libraries**: Keep symbols and footprints project-local.
4. **Never fabricate module pinouts**: Always consult official datasheets/module documentation.
5. **Preserve exposed unused module pins**: All real physical pins on modules must remain visible and receive proper No-Connect (`no_connect`) flags where applicable.
6. **Strict Power Pin Elevation**: Positive power (`VBUS`, `VBAT`, `5V_SYS`, `3V3_SYS`) in the upper region; Ground (`GND`) at the very bottom. Horizontal pin exit only.

## 6. Core Capability Set

### A. Planning Before Implementation (`planner`)
- Never modify files first and reason afterward.
- Review request → inspect existing schematic state → isolate affected functional blocks → plan minimal edits → define verification steps upfront.
- Obtain approval before executing modifications (Gate 1).

### B. Systematic Debugging (`orch-fix-defect`)
- Triggered on: ERC failure, disconnected pin, wrong net, duplicate connection, power rail mismatch, pin mapping mismatch, symbol pin mismatch, missing NC, export failure, visual overlap, or unexpected regression.
- Enforce root-cause determination before applying any fix.
- Apply minimal targeted fix; never blindly refactor unrelated blocks.

### C. Verification Before Completion (`verification-loop`)
- Never claim `DONE`, `PASSED`, `FINAL`, or `READY` until verification has actually executed.
- Mandatory 6 phases:
  1. File integrity & lock verification
  2. Pin connectivity & electrical sanity
  3. KiCad CLI ERC execution & violation analysis
  4. Visual PDF/SVG export & inspection
  5. `SCHEMATIC_DRAWING_RULES.md` compliance
  6. Git / backup diff & regression review
- Must output formal `VERIFICATION REPORT [PASS/FAIL]`.

### D. Regression Review (`code-reviewer`)
- Compare `BEFORE` vs `AFTER` using diffs or visual comparisons.
- Confirm ONLY requested areas were changed.
- Verify protected power domains (`VBUS`, `VBAT`, `5V_SYS`, `3V3_SYS`, `GND`), battery ADC (`GPIO1 = ADC_VBAT_SENSE`), GPIO mapping, buses, and UI circuits.

### E. Context Budget Discipline (`context-budget`)
- Keep context small and lean.
- Do not preload unnecessary software/frontend tools or rules.
- Load specialized skills on-demand only. Normal KiCad tasks do NOT auto-invoke `context-budget`.
